# Pi shared status renderer prior art

This survey of published Pi statusline and footer packages was retrieved on 2026-10-20, before this renderer existed. It found no as-shipped renderer with semantic degradation; [ADR 0003](../adr/0003-own-renderer-publisher-split.md) records the decision to build our own. The renderer now wraps lines before degrading publisher groups. Versions, downloads and activity dates below are as retrieved.

## Verdict

**Yes: `@juanibiapina/pi-powerbar@0.16.0` is an as-shipped generic, event-fed, one-line renderer.** It can host our three extensions without modifying the renderer: usage publishes one bar segment per provider/window, PR publishes text, and capability-exposure publishes a muted segment configured on the right. **Its degradation is widest-segment truncation, not semantic full → compact → minimal variants.** If the requirement means “never clip a usage bar/number, preserve essential segments by priority,” it is **not** a complete match.

Other genuine public contribution surfaces exist: `@sentixx/pi-info`, `@aliaksei-raketski/pi-statusline`, `pi-footer`, `pi-powerline-footer`, and `pi-zentui`. None inspected combines a small renderer-only package, arbitrary external segments, strict one-line semantic degradation, and producer-defined priority/variants as shipped. “No existing shared renderer” would be an incorrect conclusion; “no exact semantic-layout contract” is supported by this bounded search.

## Scope and evidence

- Retrieved **2026-10-20 UTC**. Published versions, not GitHub HEAD, are authoritative below. All 14 requested tarballs and 16 additional published packages were downloaded using `npm pack --ignore-scripts` and unpacked locally; those snapshots were not kept. Code links below point at the same published files on unpkg, pinned to the inspected version. Supporting `@nicknisi/pi-shared@0.7.0` (the exact dependency of the inspected Nicknisi footer) was also packed. No extension was installed, loaded, or changed.
- **S** = source-observed; **R** = README-only claim; **U** = unverified. Code links label exact file:line ranges; source-reading conclusions are static, **not terminal/runtime compatibility tests**.
- Search: npm registry searches `pi statusline`, `pi extension segments`, `statusline provider api`, `pi.events statusline`, `oh-my-pi statusline`, `pi footer widget`; GitHub repository searches plus code searches for `powerbar:update`, `__piStatusbarRegistry`, `setFooter registerSegment`, and statusline event channels. The raw search responses were saved during the research and not kept. This is not an exhaustive survey of every dotfiles repository or npm result.
- **Plain status contribution ≠ segment API.** In the tables, **status-only** means another extension can call Pi's `ctx.ui.setStatus(key, text)`, and this footer reads `footerData.getExtensionStatuses()`. It does not provide individual layout, priorities, callbacks, or responsive variants. **No API found** means no external contribution surface was found in the inspected entry/rendering/registry source, not proof about every past version.

## Best match: powerbar (S)

- Contract: `pi.events.emit("powerbar:register-segment", {id, label})` populates the settings catalog; `pi.events.emit("powerbar:update", {id, text?, suffix?, icon?, color?, bar?, barSegments?})` upserts live data. An update without truthy `text` and without `bar` removes it. Event listeners: [src/powerbar/index.ts:22–39](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/index.ts#L22), [src/powerbar/index.ts:62–129](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/index.ts#L62).
- The renderer returns **one line** from `setWidget("powerbar", factory, {placement})`, above or below editor, **and hides the native footer with an empty `setFooter`**: [src/powerbar/index.ts:72–98](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/index.ts#L72), [src/powerbar/index.ts:174–192](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/index.ts#L174).
- Left/right ID arrays select and order content; unknown/unlisted IDs are not displayed automatically. `color: "muted"` is supported and is also the default. Bars support 0–100 percentages, continuous or discrete blocks. Source: [src/powerbar/settings.ts:11–18](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/settings.ts#L11), [src/powerbar/settings.ts:71–95](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/settings.ts#L71), [src/powerbar/render.ts:92–125](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/render.ts#L92).
- Width fitting repeatedly truncates the widest segment, then pads between left/right, then clamps the whole line: [src/powerbar/render.ts:157–225](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/src/powerbar/render.ts#L157). No wrapping, no semantic variants or priority. At extreme widths the right segment can still disappear in the final clamp; bars can be clipped mid-content. Unsanitized producer newlines are another boundary: producers must send single-line text.
- Integration is producer work **in our extensions**, not a renderer fork: register namespaced IDs, emit updates/removals, configure IDs into `left`/`right`. No claim that our existing packages already emit this contract; their source was outside this task.
- Operational cost: the package also ships built-in model/git/token/subscription producers and bundles `pi-usage`; it is not purely the renderer. Configure Pi's supported extension selection if those are unwanted. Settings use `@juanibiapina/pi-extension-settings`; README requires that extension loaded before powerbar and powerbar before producers ([README.md:13–15](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/README.md#L13), [package.json:22–46](https://app.unpkg.com/@juanibiapina/pi-powerbar@0.16.0/files/package.json#L22)). Range dependencies and `getFgAnsi` usage mean current Pi-version/theme compatibility needs a smoke test; no OMP parity inferred from Pi support.

## Decision for our extensions

1. **Use as shipped, if character-level one-line degradation is acceptable:** powerbar. Add small event publishers to our three extensions and supported configuration for left/right IDs. No fork, vendoring, or private renderer API is required. Per-provider usage bars are directly supported; right-aligned muted capability text is directly supported; PR is a normal text segment.
2. **If clipping bars is unacceptable:** consider Zentui's configured one-line, atomic-value omission (`responsive:false`), trading a small renderer for a substantial UI suite. It can drop whole provider values; it does not provide producer-supplied compact variants. Do not assume `compactMaxLines:1` avoids its earlier two-row reflow.
3. **If “responsive” requires semantic variants, priorities, width callbacks and essential right-slot retention:** no full as-shipped match established. Do not quietly fork a footer or provide a custom renderer module and call it upstream configuration. Seek an upstream contract change or explicitly approve custom ownership separately.

**Unverified:** current installed Pi/OMP runtime compatibility, narrow-width/theme live behavior, shared-module identity for registry imports across duplicate installations, accessibility/terminal glyph support, and producer changes needed in our actual three packages. These findings justify a focused smoke test, not a claim that integration has already shipped.
